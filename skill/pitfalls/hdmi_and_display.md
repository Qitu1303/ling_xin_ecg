# K4 · 踩坑清单：HDMI 与显示篇（14 条）

> 适用：`[PYNQ 通用]` 基于 `pynq.lib.video` 与官方 base overlay 的显示链；性能条目对任何"慢 CPU 上 Python 逐帧绘制"场景通用。

## K4-1 厂商框架已提供能力 → HDMI 零自写 RTL `[PYNQ 通用]`

- **现象**：把"自写 TMDS 编码 + OSERDES + 像素时钟域 + CDC"列入必做项（多算几百 LUT + 一个时钟域）。
- **触发条件**：看到"板载 HDMI 直连 PL 引脚、无发送芯片"这类**硬件连接事实**，据以推断"必须自己写驱动 RTL"。
- **根因**：把硬件事实当实现义务；PYNQ 官方 base overlay 已带整套 HDMI 前端 IP 与 `pynq.lib.video.HDMIOut`。
- **排查步骤**：判定"要不要自己写 RTL"的顺序：① 官方框架/参考设计有没有现成 IP？② 有没有上层驱动（Python/C）？③ 两者都无，才评估自写工作量。查能力直接看框架自带 API 清单（`pynq.lib` 下有哪些驱动）。
- **已验证效果**：`configure() + start() + newframe() + writeframe()` 出图，零自写 RTL；推翻旧结论时在文档里写明"错在哪"。
- **来源**：显示方案初期的方向修正。

## K4-2 Zynq-7000 级 PYNQ 板官方只保证 720p `[PYNQ 通用]`

- **现象**：纠结 1080p 出不了图。
- **触发条件**：想把板载 HDMI 提到 1920×1080。
- **根因**：官方文档明示：PYNQ-Z1/Z2 的 DVI 前端标称可达 1080p，但因差分引脚速度等级 **官方仅支持到 720p**（支持列表中 1080p 带"未达规范"星标）。
- **排查步骤**：分辨率锁 **1280×720** 打通，别为 1080p 折腾；采集卡侧 UVC 也要对齐 720p。
- **已验证效果**：板子 720p + 采集卡 720p 全链路跑通。
- **来源**：官方文档与实测对照。

## K4-3 出图顺序写死：`configure → start → newframe → writeframe` `[PYNQ 通用]`

- **现象**：`'MM2SChannel' object has no attribute '_cache'`（详见 K1-3）。
- **触发条件**：把官方示例"简化"时删掉 `start()`。
- **根因**：帧缓存在 `start()` 里建立。
- **排查步骤**：顺序写死四步；不确定先探针；**改写已跑通的代码要逐行对照**，别删带副作用的调用（`start()/stop()/allocate()`）。
- **已验证效果**：含全部四步的自检脚本可一步定位卡点。
- **来源**：同 K1-3。

## K4-4 静态纯色无法判活 —— 必须用动态画面 `[通用]`

- **现象**：PC 端一直黑；或"昨天好、今天不出图"。
- **触发条件**：只推一帧静态彩色/黑帧就判定"通路坏了"。
- **根因**：静态纯色分不清"通路活着"与"PC 卡在最后一帧"；且**纯黑帧 vs 无信号**肉眼不可分。
- **排查步骤**：黑白轮换 ~20 s（40 次 × 0.5 s）或色块从左滚到右（`frame[:] = 0; frame[300:400, x:x+100, :] = 255; writeframe`，步进推进），**画面在变 = 通路活着**；先分清屏幕上是"**无信号**"（→ 查时钟/TMDS）还是"**黑色画面**"（→ 查数据通路）。
- **已验证效果**：色块移动被 PC 侧看到 → 判活成立。
- **来源**：某次"PC 端全黑"的判活实验。

## K4-5 USB 采集卡自己叠"分辨率不匹配"提示字（不是板子/驱动错） `[通用]`

- **现象**：PC 画面出现多语言提示文字 + 红边框（"HDMI resolution is smaller than UVC capture..."）。
- **触发条件**：HDMI 源 720p 接采集卡，采集卡默认 UVC 输出 ~1080p。
- **根因**：采集卡固件自己渲染并叠加提示；UVC 分辨率 > HDMI 输入分辨率。
- **排查步骤**：OBS → 该采集设备来源 → 属性 → **分辨率/FPS 类型 = 自定义 → 1280×720** → 提示字消失。反向修法（源切 1080p）不推荐（见 K4-2）。**重要副产品：能看到这段字 = HDMI 信号已经进 PC 了**，别再往硬件方向查。Windows 自带"相机"不给分辨率选项，必须用 OBS/厂家工具。
- **已验证效果**：改 OBS 分辨率后提示字消失、画面正常。
- **来源**：某次"画面有红字"的误报排查。

## K4-6 板子有两个 HDMI 口：插 IN 必黑 `[通用]`

- **现象**：PC 完全无信号。
- **触发条件**：板子 HDMI OUT（源）与 HDMI IN（sink）两个口都在，插错。
- **根因**：接法错——OUT 才是信号源，IN 是接收口。
- **排查步骤（排查树）**：① 板上插的是不是 **OUT** 口 ② 采集卡+线是否已用别的 HDMI 源自证 ③ 采集软件选中的设备对不对。**PC 侧先自证（5 分钟，别省）**。
- **已验证效果**："PC 侧先自证"固定为第 2 步后，避免了把采集卡问题误判成板子问题。
- **来源**：某次出图速通的排障树。

## K4-7 帧缓冲字节序要实测标定，直觉配色会红绿错 `[PYNQ 通用]`

- **现象**：颜色不对（红绿互换等）。
- **触发条件**：直写帧缓冲时按"写 X 应显 X"的直觉配色。
- **根因**：帧缓冲字节序与应用层通道排列不一致（直写实测某位置序列：pos0→显示绿、pos1→蓝、pos2→红），交换排列应为 **`[1, 0, 2]`**。
- **排查步骤**：**直写帧缓冲 + 长驻留（≥3 秒/色）逐色确认**，不要靠帧刷新时序下的目测；旧记录若与标定矛盾，以标定为准。
- **失效条件**：仅对"直写 PYNQ 帧缓冲"路径成立；走 `pynq.lib.video` 的 `PIXEL_*` 常量时以库语义为准。
- **已验证效果**：三色标定后显示代码改为 `[1,0,2]`，干跑断言全绿（板上复测建议照 K4-4 动态画面再确认一次）。
- **来源**：某次颜色通道排查。

## K4-8 自建视频链黑屏：先物理与板子状态，再按概率排下游 `[通用]`

- **现象**：软件链路全通（建链成功、推送计数上涨）但屏幕无画面；且官方 base "昨天好、今天不出图"。
- **触发条件**：PL 被反复重配（多版 bit 来回顶）的联调期。
- **根因**：逐层排他后定位——本轮真根因是时钟跨区域偏斜（见 K3-6），软件层排查无法发现，必须先排除物理/状态层再进时序深水区。
- **排查步骤（顺序即纪律）**：① 物理三件套（线两端重插、确认 OUT 口、显示/采集输入源没被切走）② **断电重启板子**（最便宜的一步）③ 干净官方通路复测（`BaseOverlay` + `hdmi_out` 推 10 帧，不经自研模块）④ VDMA 状态诊断（`running` 状态位/帧缓冲地址，区分"VDMA 没流出"vs"流出但下游挂"）⑤ 下游按概率：像素时钟（时钟未锁定则无信号）→ 自建 IP 数据通路（首次上板压成全 0 即纯黑）→ 编码器时钟档位 → TMDS 引脚定义。
- **已验证效果**：本轮真根因是 K3-6 的 BUFR 跨区域偏斜——按此顺序排除完物理/重启/官方通路后才进入时序深水区，一天内闭环。
- **来源**：某版显示链多轮联调。

## K4-9 显示驱动的参考时钟要求（如 axi_dynclk 硬编码 100 MHz） `[PYNQ 通用]`

- **现象**：显示驱动搜索时钟失败 / 像素时钟对不上。
- **触发条件**：自建 BD 里给可编程像素时钟 IP 的参考时钟不是它要求的值。
- **根因**：PYNQ 显示驱动的时钟搜索算法**硬编码 100 MHz REF**（真实源码在 `pynq/lib/_pynq/_video/video_display.c`）。
- **排查步骤**：用 clocking wizard 从 FCLK0（板上实际频率）**全整数分频合成 100 MHz** 供其参考 + VDMA/HP 口；PS FCLK 侧想加第二个时钟可能撞门控参数（见 K2-1），别走那条路。
- **已验证效果**：31.25 MHz × M32/D1/O10 = 100.000 MHz 全整数合成，显示链正常。
- **来源**：某版 BD 时钟树设计。

## K4-10 720p 像素时钟实测 ≈74.286 MHz（名义 74.25），可 dump 反推 `[PYNQ 通用]`

- **现象**：想确认板上真实像素时钟，文档只给名义 74.25 MHz。
- **触发条件**：调像素时钟参数、写 `create_clock` 或核算链路。
- **根因**：可编程像素时钟 IP 内部由 MMCM + 分频比（BUFR 等）共同决定实际输出，与名义值存在千分之几偏差。
- **排查步骤**：dump 时钟寄存器按分频比反推（实测 `100 MHz × 52/(7×2) ÷ 5(BUFR) ≈ 74.286 MHz`，误差 0.05%）；约束侧写 13.333 ns（报告值 75.002 MHz 口径）即可。
- **失效条件**：分辨率换成 640×480/800×600 时该值不适用，需重算。
- **已验证效果**：时序报告 `clk_pixel` 13.333 ns，DRC 通过、出图正常。
- **来源**：同 K4-9。

## K4-11 显示侧性能三板斧：cached 离屏缓冲 / `fill()` 清屏 / flat 散射绘制 `[PYNQ 通用]`

- **现象**：单帧渲染 610 ms；采集速率被拖到一半以下；丢样 ~11/s。
- **触发条件**：逐帧绘制时：① 绘制缓冲落在与 VDMA 帧缓冲同一块 **uncached CMA**（`np.empty_like(frame)`）；② 元组广播清屏 `buf[:] = (0,0,0)`；③ Python 逐列循环画波形。
- **根因**：① uncached 内存上全帧 numpy 操作慢 10~20 倍；② **元组广播 fill 在 A9 上无 SIMD 快路径**（~30 cycles/元素，2.76 M 元素 = 127 ms）；③ A9 上 Python 解释器开销约是 x86 的 40 倍。
- **排查步骤**：① 绘制全部在普通 cached 缓冲完成，仅最后 `frm[:] = buf` 一次 memcpy（~10 ms）；② 纯色填充用 `arr.fill(标量)`（memset 快路径 **2.5 ms，49 倍**差距）；③ 稀疏波形用 **flat 散射法**（`np.repeat` 展开索引 + fancy 散射写，代价正比波形像素数）。**向量化选型必须上板微基准**：x86 上最快的写法在 A9 上不是最快（实测 x86 列循环 1.0 ms 最快；A9 上 flat 散射 72.3 ms 最快、掩码法 139.9 ms）。
- **失效条件**：cached 与 uncached 上"元组广播写"同慢——慢在 numpy 循环不在内存，别把清屏归因到 uncached（判据：cached 版同样 127 ms）。
- **已验证效果**：单帧 610 → 252 → **127 ms**；软件口径速率 15.2 → 30.4+；波形段 211 → 2.4 ms。
- **来源**：某日"采集被渲染拖慢"排查（方法学见 P2 工作流）。

## K4-12 渲染帧率节流在"单帧耗时 > 间隔"时失效 `[通用]`

- **现象**：`max_fps` 任何取值都无效（5↔25 实测丢样几乎不变）；渲染线程满负荷持锁，把采集轮询拖慢数倍。
- **触发条件**：节流写 `wait(max(0, 1/max_fps − 单帧耗时))`。
- **根因**：单帧耗时 > 间隔时 wait(0)，节流形同虚设；且渲染持 GIL 挤占采集。
- **排查步骤**：判别：直调最重函数 ×N 计时（实测 p50=610 ms > 判据 200 ms；渲染线程实跑 1.57 fps ≈ 1000/610 = 满负荷坐实）。修法：过渡定 `max_fps=1`；根治 = 显示帧与绘制帧**解耦**（三帧池 newframe/writeframe 轮换 + 分块写 + 帧间主动长睡）。**单纯降频只减少冻结次数、不减单次冻结杀伤力——先砍单次耗时**。
- **已验证效果**：解耦后 `update()` 实测 ~2 µs/次；采集速率恢复满值、丢样 ≈0。
- **来源**：同 K4-11。

## K4-13 显示对象必须显式传工程 overlay（"自动模式"会载 base 顶掉工程 bit） `[PYNQ 通用]`

- **现象**：跑着跑着采集速率掉、`overlay.device.bitfile_name` 变成 `base.bit`。
- **触发条件**：显示封装走"自动模式"自建显示对象。
- **根因**：自动模式加载官方 base overlay，把工程 bit 顶掉（寄存器地址全变）。
- **排查步骤**：显示对象**显式传工程 overlay**；判别三件套之一就是 `bitfile_name` 是否仍是工程 bit（见 K1-1）。
- **已验证效果**：该口径写入项目红线后此类症状绝迹。
- **来源**：某次主循环速率漂移排查。

## K4-14 HDMI 出图 + 画面叠文字（纯 Python，零自写 RTL） `[PYNQ 通用]`

- **现象**：需要在波形上叠加数值/状态文字。
- **触发条件**：`HDMIOut` 没有内置文字 API。
- **根因**：框架不提供文字渲染——文字必须自己渲染成像素再合成进帧缓冲。
- **排查步骤**：① `frame = hdmi.newframe()` 得 H×W×3 numpy uint8 帧缓冲；② 波形层用 numpy 向量化写像素（`frame[ys, xs, :] = color`），**别用 Python 逐像素循环**；③ 文字层用 PIL：`Image.fromarray(frame)` → `ImageDraw.Draw(img).text(...)` → `np.array(img)`；④ `writeframe(frame)` 整帧推送（非增量）。PIL 默认字体**不含中文**（需 `.ttf` + `ImageFont.truetype()`）；分辨率先上 720p。
- **失效条件**：每帧都要重新合成后整帧推；PIL 全帧操作在 A9 上有成本（实测三处文字 ×3 = 18 ms 可接受，更大工作量需上板评估）。
- **已验证效果**：波形区像素映射与文字层耗时（18 ms）均在预算内。
- **来源**：某次显示层功能扩展。
