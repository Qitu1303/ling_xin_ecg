# K1 · 踩坑清单：PYNQ 板上运行篇（15 条）

> 适用：PYNQ 框架（2.x/3.x，条目内注明版本差异）。每条格式：现象 / 触发条件 / 根因 / 排查步骤（含判别实验）/ 已验证效果 / 来源。通用性标注见每条标题。

## K1-1 新建封装对象/重载 Overlay 后使能回零 → 实测速率 0.0 `[PYNQ 通用]`

- **现象**：`ValueError: 实测速率 0.0 不合理`；或自检能过、下一格测量返回 0.0。
- **触发条件**：Jupyter 多单元格流程；每个"新建 Overlay 封装对象"的单元格都等于一次重下载 + 控制寄存器复位；上一格的收尾把使能写了 0 也会留下同症状。
- **根因**：`Overlay(bit)` 默认重配 PL → 控制寄存器回默认值（使能=0），而封装对象的构造**不自动启动**；随后的采集/测量一进来就量到 0。
- **排查步骤（30 秒判别三件套）**：① 读控制寄存器（使能位=0？）② 读 `overlay.device.bitfile_name`（变成 `base.bit` = 被显示"自动模式"顶掉；仍是工程 bit = 没顶掉）③ 计数器 1 s 增量。三者区分「未使能 / PL 被顶 / 真硬件故障」。修法：新建后**立即启动**；一切显式传实测速率。
- **已验证效果**：自检 10 关全过后下一格报 0.0，三件套判得"纯忘使能"，一行 start 救活；不同人写的脚本首次上板复现同款。
- **来源**：某次板测排障：checkup 与主循环分格之间被收尾格清了使能。

## K1-2 `Overlay(bit, download=False)` 后访问寄存器 = bus error 挂内核 `[PYNQ 通用]`

- **现象**：Jupyter kernel died（bus error），现场全丢。
- **触发条件**：做"官方 base vs 自研 overlay"的 A/B 对照；任何"只读元数据不动 PL"的场合。
- **根因**：`download=False` 只解析元数据 + 加载 Python 驱动，**不重配 PL**；PL 里跑的还是上一个 bit，base 的寄存器物理地址在当前 bit 的地址空间里不存在 → MMIO 一读就挂。
- **排查步骤**：访问寄存器前先问"**这个 overlay 的 bit 现在真在 PL 里吗**"；结构对照（ip_dict/hwh 文本层）不需要 download，**行为/寄存器对照必须真下载**，对照完把工程 bit 重载回来；A/B 一次只变一个量。
- **已验证效果**：把 A 的 Python 侧与 B 的 PL 侧拼在一格 → 内核挂、对照作废重排。
- **来源**：某版显示链联调的 A/B 对照实验。

## K1-3 `newframe()` 报 `'MM2SChannel' object has no attribute '_cache'` `[PYNQ 通用]`

- **现象**：`AttributeError: ... no attribute '_cache'`（栈在 `pynq/lib/video/dma.py`）。
- **触发条件**：`configure()` 之后直接 `newframe()`——把官方示例"简化"时顺手删掉 `start()`。
- **根因**：`pynq.lib.video` 的帧缓存 `_cache` 在 `start()` 里才建立，不在构造函数。
- **排查步骤**：顺序写死 `configure(mode, pixel_format) → start() → newframe() → writeframe()`；不确定先探 `hasattr(<hdmi对象>._vdma.writechannel, '_cache')`。改写已跑通的代码要逐行对照，别删"看着多余"的带副作用调用。
- **已验证效果**：含 `start()` 的版本全程无异常；删掉立刻报错；补回后探针 = True。
- **来源**：某次 HDMI 出图脚本的两次对照实验。

## K1-4 Jupyter Upload 只落 notebook 所在目录 + 独立格收尾副作用 `[PYNQ 通用]`

- **现象**：① 传了两次文件板上行为没变（跑的还是旧默认值）；② 正式流程三档全崩（漏投 91%、显示拦帧数千、输出全 nan）。
- **触发条件**：① 上传子目录里的文件；② 正式流程前跑过任何"带收尾的独立格"（结尾 close/stop + 自建封装对象 → 重下 overlay → PL 重配 → 使能全局回零）。
- **根因**：Upload 的落点是"当前 notebook 所在文件夹"，进不了子目录；独立格的收尾动作破坏后续格对旧对象的复用。
- **排查步骤**：① 传完必跑"查找+搬运"自修复格（glob 全盘搜 → 校验字节/MD5 → 搬到正本 → 回读校验，见 T3 模板）；② 正式流程 = 干净 kernel 一次跑完，中途不插带收尾的独立格；验收取证放流程前或另开 kernel。
- **已验证效果**：修法落地后连续三次板测一轮跑完；`close()` 会连带关闭显示，"重开显示只能整场重来"。
- **来源**：某次多组件交付上板的两次事故。

## K1-5 板载时钟不可信 → 文件名/时间戳/"最新文件"全不可信 `[PYNQ 通用]`

- **现象**：按时间排序取"最新"产物拿到旧文件；session 名日期停在镜像发布日附近。
- **触发条件**：板上未同步 NTP / 未 `sudo date -s`；从板上拉产物到本地分析。
- **根因**：板载系统时钟停在旧日期，所有时间戳与目录名都基于它。
- **排查步骤**：取文件按**内容特征**辨认（样本数、起始样本号、summary 字段）；新拷数据先与旧组做 MD5/行数对照；版本一律以哈希为准。
- **已验证效果**：两组"新拷"产物被 MD5 当场识别为旧副本（字节级相同），避免一整轮误判。
- **来源**：某日离线取证被带偏一轮后的复盘。

## K1-6 板上 numpy 只用长期稳定 API；板上只有 numpy 没有 scipy `[PYNQ 通用]`

- **现象**：上板 `AttributeError` / 行为差异；`import scipy` 直接失败。
- **触发条件**：本地用 NumPy 2 专属 API；或代码引了 scipy/matplotlib。
- **根因**：板端 Python 3.10 自带 numpy 较旧且不便升级；官方镜像只保证 numpy + 标准库。
- **排查步骤**：只用 `percentile / hanning / polyfit / interp / rfft` 等稳定接口；"板上才跑的模块必须本地真 import 一次"；按"最不利口径"离线验证（用板端历史实测的低速率跑最重负载的长会话）。
- **已验证效果**：交付包全部只用 numpy + 标准库；用"低速率 × 长会话 × 全组件"做最不利离线验证通过。
- **来源**：某次交付前环境核对。

## K1-7 `py_compile` 通过 ≠ 能 import（`NameError: lru_cache` 类） `[PYNQ 通用]`

- **现象**：本地语法检查通过，板上 import 直接 `NameError`（类体装饰器求值时炸）。
- **触发条件**：把只能在板上跑（`__init__` 里探测硬件失败就 raise）的模块交付前只做语法检查。
- **根因**：`py_compile` 只验语法，验不出"名字未定义"。
- **排查步骤**：① `python -c "import <模块>"`（import 会执行类体与装饰器）；② 更狠：`Cls.__new__(Cls)` 绕过 `__init__` + 手工补字段 + **假硬件对象**把计算/绘制全路径干跑多种输入（正常值/负值/越界/单点）。
- **已验证效果**：干跑 4 类输入全过后上板零 import 惊喜。
- **来源**：某次显示模块交付的返工。

## K1-8 运行时热改 PL 时钟（写 SLCR `FPGA0_CLK_CTRL`）会把 PL 搞停摆 `[Zynq 通用]`

- **现象**：寄存器读回确认改成功，但紧接着逻辑计数器每秒增量变成 **0**（AXI 从机疑似半状态死锁）。
- **触发条件**：想在 PYNQ 里运行时改 FCLK 频率去迁就写死的分频参数。
- **根因**：Zynq PL 时钟是"热切换"，须按规程（先关时钟使能 → 改分频 → 再开使能）才无毛刺；直接改分频产生毛刺/停摆。
- **排查步骤**：不要运行时改 PL 时钟；要适配就**改设计参数**（把逻辑里的频率常量改成板上实测值 → Re-Package → 重综合出 bit）；真实频率用"设计里已知频率的信号"反推。恢复 = 写回原值 + 重载 overlay，仍不行断电重启。
- **已验证效果**：实测计数增量归零；恢复脚本读回的分频值还被第三方改过——印证"PL 时钟控制权不在设计手里"。
- **来源**：某次"不改 bit 只改时钟"的尝试。

## K1-9 `ip_dict['x']['base_address']` → KeyError；`clock_dict[0].frequency` → AttributeError `[PYNQ 通用]`

- **现象**：照网上示例取基地址/查频率，直接 KeyError/AttributeError。
- **触发条件**：PYNQ 3.x 上按旧教程写法访问。
- **根因**：PYNQ 3.x 的 `ip_dict` 条目**没有 `base_address` 键**；`clock_dict` 的值是**普通 dict**（print 出来像对象）。
- **排查步骤**：寄存器**首选属性访问** `ol.<hwh 里的实例名>`（`.write(offset,val)` / `.read(offset)`，offset 相对 IP 基址）；要知道键名就 `print(ol.ip_dict['<实例>'])`；`type(ol.clock_dict[0])` 先判型。兜底 `MMIO(基址, 长度)`（长度要覆盖最大偏移）。
- **已验证效果**：改正后两条不同 IP 链路都跑通；错误写法曾进过文档、随后就地更正——**引用他人代码先跑一遍再信**。
- **来源**：最小工程教学与采集工程各踩一次。

## K1-10 "读清"语义寄存器：采集运行时读它 = 偷样本 `[通用（含硬件接口设计教训）]`

- **现象**：诊断脚本采数导致正式链路漏样；"新数据"标志读到恒 0。
- **触发条件**：在采集循环运行时额外读数据寄存器；把"读清"条件写成"任何一次读都清"。
- **根因**：硬件侧"读一次清一次标志"的设计 + 软件侧诊断直接读数寄存器 → 正常轮询的标志被诊断读走；RTL 里读清条件若不限定地址，读别的寄存器也会误清。
- **排查步骤**：诊断采数一律走**快照缓冲**，别碰读清寄存器；硬件侧读清条件用"读命中 + 地址匹配"双重限定；接口文档里给每个寄存器标清"读是否带副作用"。
- **已验证效果**：诊断格定型为"只读快照"；RTL 侧读清逻辑改对后标志才可靠。
- **来源**：某次诊断格设计复盘。

## K1-11 产样率双口径：硬件产样率 ≠ 软件投递率 `[通用]`

- **现象**：基于周期性的统计量系统性放大 1.2~1.7 倍（时间轴错）。
- **触发条件**：用硬件计数器口径（`sample_cnt` 类）当时间轴标定；或在主负载建立之前测标定值。
- **根因**：PS 软件实际投递率可比硬件低 20%+（负载挤占）；标定值烧进时基前没标注口径来源。
- **排查步骤**：凡按样本号折算时间的消费方一律用**软件实测口径**（`est_fs_sw` 类）；标定测量搬到最终负载建立之后；运行期周期性重标定并限频；判据按"期望值 = 假设频率/实际频率"折算后再判定。注意"合理性检查通过 ≠ 口径正确"——区间太宽会恰好放过唯一错法。
- **已验证效果**：修后标定值与软件口径贴合、重标定次数可控。
- **来源**：某次"统计量系统性偏快"的取证（k 扫描 + 真值带反解 fs + 样本域双计数判别）。

## K1-12 PYNQ 3.1.1 的 Overlay 用 pynqmetadata 解析 hwh（不是旧 `hwh_parser`） `[PYNQ 通用]`

- **现象**：离线用旧解析器一切正常、板上却报属性缺失；直连 PS7 `IRQ_F2P` 的中断不被登记。
- **触发条件**：按官方旧源码行为推断板上行为；中断直连 PS7 不经 interrupt controller。
- **根因**：PYNQ 3.1.1 走 pynqmetadata（`RuntimeMetadataParser`），旧 `_HWHZynq` 只在部分重配置路径被用；pynqmetadata 的中断视图**只登记挂在 axi_intc 上的中断**。
- **排查步骤**：先确认解析路径；板上 A/B 判别：旧解析器直跑 vs `Overlay()` 对比 `interrupts`；自建 BD 的中断优先对齐官方 base 结构（IP → xlconcat → axi_intc → PS7 IRQ_F2P）。
- **已验证效果**：直连版本 `interrupt_controllers={}`；官方 base 控制器 61 号 raw irq、30 条引脚齐全。
- **来源**：某版中断链集成的排障。

## K1-13 板上包 ≠ 本地副本：路径/行号/阈值都可能不同 `[通用]`

- **现象**：板上 traceback 的路径与行号在本地源码里对不上；同一函数板上/本地默认参数不同。
- **触发条件**：读板上 traceback 按本地行号断言板端逻辑。
- **根因**：板端包版本比本地新、目录布局不同。
- **排查步骤**：路径/行号对不上属正常；要断言行为就打印板上 `inspect.signature` / `inspect.getsource` 特征串，**以板上为准**。
- **已验证效果**：板端速查格统一加"第 1 格打印板上真实签名"后不再误判。
- **来源**：某次跨环境 traceback 比对。

## K1-14 板上 Jupyter "没响应"可能只是浏览器问题 `[PYNQ 通用]`

- **现象**：单元格不执行/输出不刷新；脚本本身没问题。
- **触发条件**：非 Edge 浏览器访问 `http://<板IP>:9090`。
- **根因**：浏览器侧兼容问题。
- **排查步骤**：先换 **Edge** 重开一次再谈别的；分清两类"没响应"——浏览器侧（换浏览器即好，无 traceback）与内核侧（提示符 `In [*]` 且抛明确 traceback，换浏览器无用）。
- **已验证效果**：同一脚本换 Edge 直接跑通。
- **来源**：某次板测开头 20 分钟的消耗。

## K1-15 PYNQ 上电启动三段判据（LED / 跳线 / 串口） `[PYNQ 通用，板级细节以你的板卡为准]`

- **现象**：镜像起不来时分不清"卡在探测"还是"在等卡"。
- **触发条件**：新烧卡首次启动、启动失败排查。
- **根因**：失败原因分布在供电/存储/镜像三层；内核并行探测、打印顺序不固定。
- **排查步骤**：三段判据——① 上电：电源红灯亮（查供电跳线/USB 供电）② bitstream 加载：DONE 灯亮（查 SD 卡是否到位、启动跳线拨 SD、重烧镜像）③ 系统起来：约 1 分钟后板上 LED 组合闪烁。串口头三行认镜像身份：`Linux version ...-xilinx-vYYYY.N` / `Kernel command line:` / `Machine model:`。**别用"日志最后一行"反推**卡点，用"有没有挂载根文件系统 / 有没有登录提示 / LED 组合"。
- **已验证效果**：官方镜像也有过"静默挂死"（停在 USB 探测行之后、无 SD 注册行）——按此判据确认后**重做卡换版本**一次启动成功；锁版本（镜像 + 板卡型号）是硬纪律，重做卡排在查硬件之前。
- **来源**：某次新卡首启排查。
