# P1 · 提示词工作流：离线全绿、上板"哑"的排障三板斧

- **类型**：提示词工作流
- **适用场景**：同一份代码离线仿真/回归全绿，上板后"零现象 / 现象不符"；或任何"只在板上出现"的时序类问题（启动停顿、在线重标定、缓冲欠账、投递率塌陷）。
- **使用方法**：把下面【提示词模板】整段发给 AI（或自查时按步骤走），把 `<变量表>` 中的占位符换成你的工程实际值。
- **失效条件**：板上日志必须已 `tee` 落盘且收尾统计字段齐全；若只截屏了几行，第 ②③ 板的真值拿不到，流程退化为猜测。另外本工作流只负责**定位**，改码须在根因被判别实验钉死之后。
- **已验证效果**：某次板上联调中，"事件卡片零输出"问题在**动手改代码之前**就把整链根因钉死（启动停顿 → 合成源追发欠账 → 假采样率 → 在线重标定清空检测窗），一次修复到位，回归零重标定。
- **来源**：某次板上联调：新插件首次上板后剧本"零现象"，靠三板斧发现"零现象本身是假象"；同日沉淀为固定流程。

---

## 提示词模板

```text
你是一名嵌入式/FPGA 板级排障工程师。我们的工程"离线全绿、上板无现象"，
请严格按下面三板斧流程协助定位，每一板给出明确判据与产物，禁止跳步、禁止先改代码。

【背景变量】
- 板型：<BOARD>，PYNQ 镜像 <PYNQ_VER>，工程 bit：<BIT_PATH>
- 本地源树：<SRC_DIR>；板上部署包：<PKG_DIR_ON_BOARD>
- 板测日志：<LOG_FILE>（含启动横幅、标定行、收尾 stats、事件流）
- 板上记录产物：<SESSION_DIR>（含 summary 与分片 CSV）
- 离线回归基线：<BASELINE_REF>（表格或 JSON）

【第一板：先证版本（不做任何行为分析）】
1. 列出本次板测涉及的关键文件清单（源码/参数/前端资源，3~10 个）；
2. 对每个文件给出"本地 vs 板上"哈希核对方法（md5sum/sha256sum 命令与预期输出格式）；
3. 判读：全部一致 → 排除"传错版本"，问题必在行为层，进入第二板；
   任一不一致 → 先修复部署一致性（重新同步 + 上板核对格），再重跑板测。
注意：板上系统时钟可能未同步，禁止按文件修改时间取"最新"，一切以哈希为准。

【第二板：读板上日志真值（五处，逐处引用日志原文行）】
① 启动横幅：case 名 / 注入窗 / 期望输出码——确认板上跑的就是你以为的剧本；
② 标定行：fs 标定值与假设值的偏差（>±2% 即可疑，警惕"追发欠账"造成的假 fs）；
③ 在线重标定：发生时刻与次数——若落在注入窗/演示窗内，列为头号嫌疑；
④ 运行指标：轮询速率、峰峰值/量程、质量指标、漏投比例；
⑤ 收尾 stats：时长/样本数/软件口径 fs/使用口径 fs/重标定次数/事件流条数。
对每一处输出："日志原文行 → 判读（正常/异常+为什么）"。

【第三板：拉回板上产物离线重放】
1. 给出"从板上拷回 <SESSION_DIR> 到本地"的核对步骤（先对旧组做 MD5/行数对照，
   防止拿到旧副本——板上时钟不可信）；
2. 用与板上同一份检测/插件代码离线重放，输出：帧数 / 时间范围 / 事件码多重集 / 卡片簇；
3. 与板上日志逐条对照，只比"事件码多重集+卡片簇"，不比条数（帧率不同条数会差一倍）；
4. 结论句式："板上零现象 = <机制解释>；判别实验：<实验>，若现象为 <Y> 则根因坐实"。

【输出要求】
- 每一板末尾给"本板结论 + 下一板前置条件"；
- 全程不改代码；给出至少一个"不改代码就能做的判别实验"；
- 最终结论必须写明：离线复现能否覆盖该机制（注意"离线只证机制、不证幅度"）。
```

## 变量表

| 占位符 | 含义 | 示例 |
|---|---|---|
| `<BOARD>` | 板卡型号 | PYNQ-Z2（Zynq-7000） |
| `<PYNQ_VER>` | 板上镜像版本 | PYNQ 3.1.1 |
| `<BIT_PATH>` | 板上 bit 路径 | `/home/<user>/<dir>/<top>_wrapper.bit` |
| `<SRC_DIR>` / `<PKG_DIR_ON_BOARD>` | 本地源树 / 板上部署包 | `./src` / `/home/<user>/<pkg>/` |
| `<LOG_FILE>` | 板测日志（tee 落盘） | `buglog/<MM-DD>/b<N>.txt` |
| `<SESSION_DIR>` | 板上记录产物目录 | `records/session_*/` |
| `<BASELINE_REF>` | 离线回归基线 | 回归表 / baseline JSON |

## 配套纪律（模板已内置，单独摘出防遗漏）

1. **板测输出必须 `tee` 落盘**：`python3 <主脚本> ... 2>&1 | tee /tmp/<名>.log`，事后归档；日志首行贴关键文件 `md5sum` 三行，形成"版本指纹"。只靠看屏幕截几行，事后无法复盘。
2. **板上时钟不可信**：session 名与文件时间戳基于板载时钟（实测可停在镜像发布日附近）；取文件按**内容特征**（样本数、起始样本号、summary 的 `n_written`）辨认，新拷数据先与旧组做 MD5/行数对照。
3. **"离线只证机制、不证幅度"**：离线合成源"虚拟时钟不睡觉"、主循环不被堵，板上"停顿→追发→假 fs→重标定"这条链离线上根本不出现；报告里必须写明，别让人按离线数字反推板上。若离线回归里**显式注入时序扰动用例**（复刻板上停顿时长），则机制与幅度都可离线验证——这是升级版回归。
4. **判"哑"之前先查口径**：某类事件可能只到"卡片/旗子"层、不进事件流；"报出 = 事件流 ∪ 卡片层标记"双通道判定，只比事件流条数会把"达标"判成"哑"。
5. **锁死速率的合成源必须显式定义停顿语义**：按时间戳到点投递的源，被组件启动停顿（实测 ~0.4 s）欠账后若"追发补回"，会污染标定；修法 = 停顿超过阈值就丢弃欠账并计数。**阈值按最坏欠账自算，不要照抄别人的 0.5 s**（某工程实测该值会漏掉 0.384 s 的事故；建议按 0.25 s 起步并用回归验证）。

## 预期输出与判读

- 第一板输出一张哈希对照表（文件/本地哈希/板上哈希/一致?）；
- 第二板输出五处真值的"原文行 → 判读"清单，头号嫌疑带时刻戳；
- 第三板输出"事件码多重集 + 卡片簇"对照与一句根因结论 + 判别实验；
- 三板走完仍无根因 → 停，转 P2（负载归因）或查 `../pitfalls/`。

## 来源

某次板上联调：新插件轨道首次上板，剧本零现象；第一板证明版本一致，第二板第③处（重标定时刻 16 s 正落注入窗 15~35 s 正中）坐实根因，第三板把"零事件"收敛为"检测器被重标定清窗后收编了塌陷拍"。同流程在后续 12 次板测中复用，均一轮定位。
